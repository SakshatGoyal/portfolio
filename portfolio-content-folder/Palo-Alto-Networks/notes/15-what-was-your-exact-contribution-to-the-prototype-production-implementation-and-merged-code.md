# 15. What was your exact contribution to the prototype, production implementation, and merged code?

**Category:** Missing attribution boundary  
**Caliber markers:** Provenance, craft, corroboration, defensibility

**Question:** You state that you shaped the platform from problem setting to front-end build, created a CopilotKit prototype with a Codex shim and approved React components, and enabled engineering to build a scalable solution from a forked CopilotKit repository. The artifacts also show a merged pull request with motion rationale and multiple reviewers. Which code, architecture, components, interaction specifications, metrics, and production decisions were yours; what did engineering change; and what remained prototype-only?

**Reason for investigation:** The evidence is unusually concrete: terminal output, functional UI recordings, a component-selection architecture, a real merged PR, reviewer names, file changes, and a rationale for anchor animation. This is strong provenance texture. The narrative boundary is still blurry. “AI-assisted front-end development,” “I built,” “the engineering team built,” and a large merged diff could easily cause a reader to over- or under-credit the designer. Production readiness also depends on stable IDs, permissions, data access, logs, latency, model evaluation, and cost—not only component rendering.

A public-product leader will value technical fluency but still ask what product decision it unlocked. An enterprise leader will inspect security and data architecture. At Staff level, honesty about collaboration is more credible than a full-stack hero story.

**Learning objective and decision relevance:** A strong answer would draw a precise “I/we” map, show the prototype-to-production deltas, name the constraint engineering imposed, and identify collaborators who can corroborate the work. If the prototype was mainly a persuasive artifact, that can still be high-value Staff work; it should not be represented as production implementation.

## Answer

The map, drawn as precisely as I can. Mine, solely: the interaction specification for both features (anchor object contract, state model, trace step schema and rendering rules, motion spec); the tag-cluster table system; the metrics definitions; the research and synthesis artifacts; and the prototype — a Next.js app using CopilotKit to bind chat prompts to current UI context, with a shim I wrote that sent prompt-plus-context to a Codex-class code model constrained to select from a registry of approved React components and return structured props for it. The registry was the design idea embedded in the code: the model could not emit markup, only choose among components I had built — response table, tag cluster, anchor chip, trace list, metric card — so every possible response was already inside the design system. The prototype ran on synthetic demo data end to end; the terminal-and-browser recordings in the case are that system actually executing, not motion mockups.

Shared: the front-end of the internal release. I contributed production code to the AI-interaction package, and the merged PR in the case is the checkable instance: entrance/exit motion for anchor chips in the prompt entry field — ease-out on the standard flyout curve with a larger distance-to-duration ratio, so users perceive that an anchoring action occurred — four commits, roughly +2,700/−200 including keyframes applied across attachment tags and table references plus test updates, reviewed by four engineers (two front-end, the engineering lead, the design-systems engineer), tied to an open issue about chips appearing instantly. I cite that PR not because motion was the hard part but because it's provenance: a designer with commit access, review comments answered, code merged into the mainline by the standards of the owning team. There were a handful of smaller merged changes of the same species — component styling, state polish. I did not write the orchestration layer, the retrieval tooling, or the telemetry pipeline.

Engineering's, solely: everything that made it real at scale. The team took the prototype's architecture as an existence proof and rebuilt it from a forked CopilotKit repo — replacing my per-scenario shim with a typed tool registry and an orchestration layer that logged executed calls (which is what made log-derived Trace possible, and which my prototype only faked); data access, permissions, latency, and model evaluation were theirs entirely, as was the data-engineering work to expose governed sources. Two constraints engineering imposed changed the design, and I want them on the record because they were improvements: anchoring was restricted at first to objects carrying resolvable Salesforce IDs — narrower than my "any generated object" contract, and the right hardening order — and my original streaming-in of trace steps as they executed was cut for latency and simplicity in favor of rendering the completed trace, which I initially resisted and came to agree with, since progressive trace display re-created the "watching thinking" aesthetic we'd rejected.

Prototype-only, never productionized in my window: multi-anchor comparison, the snapshot artifact, the stale-anchor warning state, streaming trace, and the full inaccessible-source treatment. And the attribution boundary: "AI-assisted front-end development" in my skills list means I used code models heavily to write my own contributions — the shim, component scaffolding, the motion implementation. The judgment about what to build, the component registry idea, and the specs were mine; a meaningful fraction of the keystrokes were not. The people who can corroborate the split are the four PR reviewers, my lead PM, and the engineering lead who forked the repo — and the fork's commit history itself, which shows exactly where my code ends.
