# 7. How did anchor semantics work in complex and failure-prone states?

**Category:** The work appears not to have gone far enough  
**Caliber markers:** Craft at zoom, enterprise judgment, defensibility

**Question:** How did Anchored Follow-Ups handle multiple anchors, a row plus a column, changed or deleted records, sorted tables, duplicate names, cross-account objects, stale data, permission changes, comparing two opportunities, removing an anchor, and returning to the original context? How could a user verify the stable object ID rather than trust the visible label?

**Reason for investigation:** The polished motion is strong: row and attachment chips use an ease-out entrance and exit so users can see that an action occurred. The GitHub pull-request artifact gives unusual provenance, including the rationale, motion curve, related issue, reviewers, and merged implementation. That is valuable craft evidence. But motion confirms an anchor was added; it does not prove that the underlying object identity is correct or durable.

In a public product, wrong context causes confusion. In an enterprise sales tool, it can produce a false risk assessment, reveal another account's data, or attach a follow-up to a stale opportunity. A Staff designer should have shaped the state and error model with engineering and data partners.

**Learning objective and decision relevance:** I want the object schema, multi-anchor rules, visible error and comparison states, and testing of anchor mistakes. A strong answer would connect interaction polish to stable IDs, permission enforcement, and recoverability. If implementation focused mainly on the chip animation and prompt composition, I would credit the micro-interaction but question the system-level completeness.

## Answer

The chip is the visible tip of an object contract, and I'll give the contract first. An anchor serialized as: object type (row, column, cell, or generated-table), a stable identity — the Salesforce record ID when the object resolved to a real record, otherwise a query-result hash tying it to the generating step — a display label, a snapshot of key fields (the chip shows "Stripe Treasury XDR Expansion, $310,000, EB never on a call · close date moved twice"), the source-query reference, and the freshness timestamp inherited from the generating response. Identity, not label, is what the follow-up binds to: sorting the table, renaming the opportunity, or duplicate account names cannot retarget an anchor, because the label is presentation and the ID is the join key. That was the first fight with engineering, and the good kind — the senior front-end engineer wanted to serialize the visible row text for v1 speed; I held for the ID-bearing contract, and the production team later constrained anchoring to objects that carry resolvable IDs at all, which validated the choice by hardening it.

What the shipped internal release actually supported: one anchor at a time. Multi-anchor — row plus column, or two rows for comparison — existed as a spec with designed states and never got built; the demo flows you see (row anchor in one arc, column anchor in another) are each single-anchor. Removal is the X on the chip; removing mid-composition returns you to an unanchored prompt with your draft text preserved. Returning to original context: the response that generated the object stays in the thread above, so the trail back is the thread itself — we deliberately made anchors immutable references to *generated* objects rather than live pointers into the table, which is also the answer to "sorted tables": the anchor references the generated result, not a screen position.

Failure semantics are where I have to split designed from shipped. Designed, in the state spec I reviewed with engineering: a stale-anchor state (record updated since the generating response — chip gets a freshness warning and the response must re-query), a deleted/merged-record state (chip degrades to a labeled error, follow-up blocked), and a permission-denied state (chip renders but the step reports the source as inaccessible rather than silently omitting it). Shipped in the internal release: the stale re-query behavior in its simplest form — anchored follow-ups always re-executed against live data rather than cached response data, which converts most staleness into correctness at the cost of occasional "the numbers changed under me" surprise. Not shipped: the explicit stale warning, the deleted-record state beyond a generic error, and any real permission enforcement — the prototype ran on synthetic demo data (Stripe Treasury, Cyberdyne, and friends are placeholders), and row-level security was the production team's problem, solved after my involvement in ways I can describe only as "designed for, per the spec, with retrieval through the user's own authorization." Cross-account anchoring was implicitly safe only because scope-by-user was assumed, not because the prototype enforced it.

Could a user verify the stable ID rather than trust the label? Partially. The chip's expanded state showed key fields and the source reference — enough to catch most wrong-object cases — but we never exposed the raw record ID or a deep link from the chip itself, which the COO-office review's "logged object IDs" control correctly identifies as the missing piece. And testing anchor *mistakes* was thin: I tested wrong-object recovery in moderated sessions (users found the X and re-anchored), but nobody adversarially tested duplicate-name confusion or merge-race conditions. So: the identity model was sound and survived productionization; the failure-state surface was designed at maybe twice the depth it shipped; and motion — the part with the merged PR — was the smallest part of the system, however photogenic.
